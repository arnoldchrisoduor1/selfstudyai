Phase 5 of "self-study-ai": accounts, cloud sync, paid cloud AI credits, landing page, desktop verification, and stabilization. No CI/CD (still pending; no Jenkins, no GitHub Actions). Follow the existing .cursor rules: reusable components in the flat components folder, sections folder, pages folder, and a design-system entry (design-system/self-study-ai/pages/<page>.md and components/<component>.md) for every new page and component.

0. Prerequisites: if any synced table still uses auto-increment integer ids, add a migration to move to client-generated UUIDv7 (or ULID) primary keys so records created offline on different devices never collide. Every synced table gets: id, user_id (nullable while local-only), created_at, updated_at, deleted_at (tombstone), version. Add a Postgres implementation of the storage traits (SeaORM) alongside SQLite, with a migration set that produces the same schema; run the same repository test-suite against both backends.

1. Accounts (optional; the app must stay fully usable local-only forever):
   - Built-in auth in the api crate (no external identity provider): email + password with argon2id, email verification and password reset via an EmailSender trait (ConsoleSender for dev/tests, SMTP implementation), session cookies for web (httpOnly, Secure, SameSite), bearer tokens for desktop, logout, logout-all-devices, session list, rate limiting on login/reset endpoints, account deletion (deletes all cloud data) and full data export (JSON + original files) available to local-only users too.
   - Authorization: user_id enforced centrally in the storage layer on every cloud query, never per-handler. Add cross-user isolation integration tests (user A can never read, write, or sync user B's data on any endpoint).
   - Local-to-cloud linking: when a local-only user creates an account, offer to upload local data; nothing leaves the device until they confirm.

2. Sync (local SQLite <-> cloud Postgres):
   - Protocol: pull then push using per-record version + updated_at and a server-issued sync cursor; batched, resumable, idempotent; deletes via tombstones.
   - Conflicts: last-write-wins per record using server version for editable records (subjects, goals, topics incl. is_core, settings, question edits, flags); append-only tables (attempts, review_logs, points_ledger, usage_events, integrity_events, daily_activity contributions) merge by union and dedupe by id; card_states are NOT synced as authoritative, they are recomputed from the merged review_logs so two devices can never corrupt scheduling; points balance is derived from the merged ledger.
   - Files: original uploaded sources sync through a FileStore trait (local-disk implementation on the server for v1), referenced by content_hash, deduped.
   - Embeddings: sync chunks and vectors only when the embedding model id matches the receiving device's default; otherwise mark the source needs-re-embedding (reuse the Phase 2 re-embed flow).
   - UI: sync status indicator in the AppShell (synced, syncing, offline, error with retry), Settings > Account & sync with last sync time, devices list, manual "sync now", and a "sign out and keep local copy" option. Surface sync conflicts and errors honestly; never silently drop data.

3. Paid cloud AI with prepaid credits:
   - A server-side CloudProvider (implements the existing ai Provider trait) so signed-in users can pick "Cloud AI" without their own keys; the platform keys live only in server environment config, never in the client or logs.
   - Credits ledger (append-only, like points): credits_ledger (user_id, amount, kind: topup|usage|refund|adjustment, reference, created_at). Pricing table in config mapping model + token counts to credits (with a configurable margin). Each cloud request first checks and reserves credits, calls the provider, then settles actual usage from the response; insufficient balance returns a clear error and never calls the provider. Per-user rate limits and a daily spend cap. Reconcile with usage_events from Phase 3.
   - Top-ups: a PaymentProvider trait with a MockPaymentProvider and an admin-only manual credit-adjust endpoint for now. Do NOT integrate a real payment gateway in this phase (it needs merchant accounts); structure the trait so M-Pesa/Stripe can be added later, make top-up webhooks idempotent and signature-verified in the interface design, and document what is needed in docs/PAYMENTS_TODO.md.
   - UI: Credits page (balance, usage history by model and feature, estimated cost before running a large generation), low-balance warnings, Cloud AI option in Settings > AI providers (hidden unless signed in).

4. Landing page (apps/landing): build the real content from docs/FEATURES.md and the actual implemented features; use the ui-ux-pro-max design system and the landing.md override. Sections: hero, how it works, feature highlights, screenshots or product visuals generated from the real UI (no fake testimonials, fake user counts, or invented claims), local-first/privacy explanation, pricing (free local use plus prepaid cloud credits, matching the real model), FAQ, download/open-app calls to action (download links as clearly marked placeholders until real builds are published), footer with privacy policy and terms placeholder pages. SEO basics: metadata, OpenGraph, sitemap, robots, structured data. Must pass an axe scan and be fully static-export compatible.
